== Wie wir prüfen, ob es stimmt

Ein Test, der nie fehlschlägt, ist nicht automatisch ein guter Test. Er könnte
auch einfach nichts prüfen. Dieses Kapitel handelt nicht davon, wie man Tests
schreibt — das siehst du an jeder Datei unter `tests/unit/`. Es handelt davon,
wie man herausfindet, ob ein Test, den man gerade geschrieben hat, überhaupt
etwas taugt.

=== Ein Testläufer ohne Magie

`tests/test.h` ist knapp achtzig Zeilen lang, und das ist Absicht, kein
Zufall. Der Kopf der Datei sagt es geradeheraus:

[source,c]
----
/* Der Testläufer des Projekts. Bewusst klein und ohne Magie:
 * Ein Test ist eine Funktion, main() zählt sie auf. Mehr braucht es nicht.
 *
 *     TEST(bitmap_pset) { CHECK_EQ(1, 1); }
 *     int main(void) { RUN(bitmap_pset); return test_summary(); }
 */
----

`TEST(name)` ist nichts weiter als ein Makro, das zu `static void name(void)`
wird. Kein Testframework registriert die Funktion automatisch, keine
Reflexion sucht sie im Programm zusammen — jede Testdatei zählt ihre Tests in
`main` selbst auf, mit `RUN(name)`. Das wirkt altmodisch, verglichen mit
Frameworks, die Tests über Annotationen finden. Es hat aber einen Vorteil, der
für dieses Projekt schwerer wiegt: es gibt keine Stelle, an der Magie
passiert, die du nicht lesen könntest. Wenn ein Test nicht läuft, liegt es
nicht daran, dass ihn irgendein Mechanismus übersehen hat — er steht entweder
in der `RUN`-Liste in `main`, oder er steht nicht darin, und das siehst du auf
einen Blick.

`RUN` selbst macht drei Dinge: den Namen merken, zählen, aufrufen, und danach
melden, ob etwas fehlgeschlagen ist:

[source,c]
----
#define RUN(fn)                                                               \
    do {                                                                      \
        test_current = #fn;                                                   \
        test_failed_here = 0;                                                 \
        test_count++;                                                         \
        fn();                                                                 \
        if (test_failed_here) {                                               \
            test_failed++;                                                    \
            printf("FEHLER  %s\n", #fn);                                      \
        } else {                                                              \
            printf("ok      %s\n", #fn);                                      \
        }                                                                     \
    } while (0)
----

`CHECK(cond)` prüft eine Bedingung und merkt sich einen Fehlschlag, macht aber
weiter — die restlichen Prüfungen im selben Test laufen trotzdem, und du
siehst am Ende alle Fehler auf einmal statt nur den ersten.

Daneben gibt es `REQUIRE`, und der Unterschied ist wichtig genug, dass der
Kommentar in `tests/test.h` ihn eigens erklärt:

[source,c]
----
/* Wie CHECK, bricht den Test aber ab. Für Bedingungen, ohne die die folgenden
 * Zeilen abstürzen würden - typisch ein Zeiger, der nicht NULL sein darf. Ein
 * abstürzender Test ist schlimmer als ein fehlschlagender: er verschluckt alle
 * Ergebnisse, die nach ihm kämen. */
#define REQUIRE(cond)                                                         \
    do {                                                                      \
        if (!(cond)) {                                                        \
            TEST_FAIL("%s ist nicht wahr, Test abgebrochen", #cond);          \
            return;                                                           \
        }                                                                     \
    } while (0)
----

Der Unterschied ist der zwischen einer Prüfung, die scheitern darf, ohne dass
danach alles zusammenbricht, und einer Voraussetzung, ohne die gar nichts
mehr Sinn ergibt. `wm_create` liefert zum Beispiel entweder einen gültigen
Zeiger oder `NULL` — ruft ein Test danach ungeprüft `wm_open` auf einem
`NULL`-Zeiger auf, stürzt nicht nur dieser Test ab, sondern das ganze
Testprogramm, und jeder Test, der danach in der `RUN`-Liste steht, wird nie
ausgeführt. Deshalb steht an genau solchen Stellen `REQUIRE(m)`, nicht
`CHECK(m)`.

=== Sollbilder: ein Bild als Beweis

Der Kern des Projekts zeichnet in eine `bitmap` — Kapitel 5 erklärt, wie sie
aufgebaut ist. Ein Test, der prüfen will, ob eine Zeichnung stimmt, kann also
nicht bloß eine Zahl vergleichen. Er zeichnet, speichert das Ergebnis als PBM
und vergleicht es mit einer gespeicherten Vorlage — dem *Sollbild*. Das
übernimmt `tests/support/golden.c`, mit zwei Funktionen für zwei
verschiedene Bildgrößen:

[source,c]
----
golden_check()      für Ausschnitte, speichert P1 (Text, im Diff lesbar).
golden_check_full() für Vollbilder, speichert P4 (binär, kompakt).
----

Das PBM-Format kennt zwei Varianten, und `src/gfx/pbm.h` legt fest, wofür
welche gilt:

[source,c]
----
/* Lesen und Schreiben von PBM-Dateien (Portable Bitmap).
 *
 * Zwei Varianten, mit einer Größenregel dahinter:
 *
 *   P1 (Text)   ein Zeichen je Pixel. Ein Vollbild mit 800 x 480 wäre so rund
 *               750 kB groß. Deshalb nur für Ausschnitte - dafür zeigt
 *               "git diff" die Änderung lesbar an.
 *   P4 (binär) ein Bit je Pixel, also genau unser Speicherformat. Ein Vollbild
 *               mit 800 x 480 sind 48 000 Bytes. Für Vollbilder, und davon nur
 *               eine Handvoll.
 */
----

Rechne die zweite Zahl selbst nach: 800 × 480 Pixel bei einem Bit je Pixel
sind `800 / 8 = 100` Bytes je Zeile (Kapitel 5 leitet diese Rechnung her), mal
480 Zeilen, macht genau 48 000 Bytes — egal wie das Bild aussieht, weil P4 den
Bildspeicher unverändert herausschreibt. Ein Textsollbild desselben Bilds
wäre, wie der Kommentar sagt, rund 750 kB groß: statt eines Bits braucht ein
Pixel im Textformat ein ganzes Zeichen, und dazu kommen Zeilenumbrüche. Der
Unterschied ist mehr als das Fünfzehnfache — bei einem einzigen Vollbild. Ein
paar solche Dateien im Repository, und `git diff` würde bei jeder kleinsten
Änderung Hunderttausende Zeichen anzeigen, die niemand liest.

Deshalb ist P1 nur für Ausschnitte gedacht, kleine Bereiche wie einen
Fensterrahmen oder eine Textzeile, bei denen die Textform ihren eigentlichen
Zweck erfüllt: `git diff` zeigt eine Änderung als lesbares Bitmuster an, nicht
als unleserlichen Bytehaufen. Und diese Regel steht nicht nur im Kommentar —
`golden_check` erzwingt sie:

[source,c]
----
bool golden_check(const char *name, const bitmap *bm)
{
    if ((long)bm->w * bm->h > GOLDEN_MAX_P1_PIXELS) {
        printf("  %s ist mit %dx%d zu groß für ein Textsollbild.\n",
               name, bm->w, bm->h);
        printf("  Nimm einen Ausschnitt oder golden_check_full() für P4.\n");
        return false;
    }
    return check(name, bm, false);
}
----

`GOLDEN_MAX_P1_PIXELS` ist `256 * 256`. Ein Test, der versehentlich ein
Vollbild an `golden_check` statt `golden_check_full` übergibt, scheitert also
nicht leise mit einer riesigen Textdatei im Repository — er scheitert laut,
mit einer Meldung, die sagt, was zu tun ist. `tests/unit/test_golden.c` prüft
sogar genau das als eigenen Test, `golden_rejects_oversized_text_image`, mit
dem Kommentar: „Die Größenregel steht im Code, nicht nur in der
Dokumentation.“ Eine Regel, die nur in der Doku steht, wird irgendwann
vergessen. Eine, die der Code selbst durchsetzt, nicht.

=== Erst hinsehen, dann übernehmen

Was aber, wenn sich ein Bild absichtlich ändert — weil du dem Programm
tatsächlich beigebracht hast, etwas anders zu zeichnen? Dann braucht es ein
neues Sollbild. `make test ACCEPT=1` schreibt es:

[source,make]
----
test: all
	@PDA_GOLDEN_ACCEPT=$(ACCEPT) ctest --test-dir $(BUILD) --output-on-failure
----

`golden_check` liest die Umgebungsvariable `PDA_GOLDEN_ACCEPT` und schreibt,
wenn sie gesetzt ist, statt zu vergleichen. Das ist bequem — und genau deshalb
gefährlich. Ein Sollbild ist nur so gut wie die Prüfung, die vor seiner
Übernahme stattfand. Wer `ACCEPT=1` setzt, ohne das neu geschriebene Bild
anzusehen, überschreibt möglicherweise gerade den Beweis dafür, dass etwas
kaputt ist, mit dem kaputten Zustand selbst. Von da an ist die kaputte Version
das neue Soll, und der Test wird nie wieder etwas melden — nicht weil alles
stimmt, sondern weil niemand mehr hinschaut.

Die Regel ist deshalb: erst hinsehen, dann übernehmen. Bei einem
Textausschnitt heißt das, das PBM tatsächlich zu lesen oder die Meldung beim
Fehlschlag zu prüfen — `golden.c` druckt bei einer Abweichung den betroffenen
Bereich als ASCII-Bild in die Konsole, damit du siehst, was sich geändert hat,
ohne eine Bilddatei öffnen zu müssen. Bei einem Vollbild bedeutet es, die
`.actual`-Datei anzusehen, die bei jedem Fehlschlag neben dem Sollbild
entsteht. Wer `ACCEPT=1` blind läuft, um eine rote Testsuite grün zu bekommen,
hat am Ende keine Sollbilder mehr — nur noch Dateien, die zufällig zu dem
passen, was der Code gerade tut.

=== Mutationstests: prüft der Test wirklich das, was er soll?

Das ist die schwierigere und wichtigere Frage. Ein grüner Test beweist nicht,
dass der Code richtig ist — er beweist nur, dass die gewählten Eingaben nicht
durch den vorhandenen Fehler gefallen sind. Ob der Test einen Fehler
überhaupt *entdecken könnte*, ist eine ganz eigene Frage, und die einzige
Methode, sie zu beantworten, ist: absichtlich einen Fehler einbauen und
schauen, ob wenigstens ein Test anschlägt. Das nennt man einen
Mutationstest. Bleibt die Suite grün, obwohl der Code jetzt falsch ist, hat
sie diese Stelle nie wirklich geprüft, egal wie viele grüne Zeilen sie
ausgibt.

Das Projekt hat diese Methode mehrfach angewendet, und mehrfach etwas
gefunden. Vier Beispiele lohnen sich, weil jedes eine andere Art zeigt, wie
ein Test versagen kann, ohne dass man es ihm ansieht.

**Ein Muster, das seine eigene Prüfung unterläuft.** Kapitel 5 erklärt, dass
ein gezeichnetes Muster am Zielbild haftet, nicht am gezeichneten Objekt — ein
graues Rechteck sieht überall auf dem Bildschirm gleich aus. Der erste Test
dafür verschob dasselbe Rechteck über zwei verschiedene `origin`-Werte und
verglich die Ergebnisse. Das Problem: `PAT_GRAY50`, das Schachbrettmuster,
setzt ein Bit genau dann, wenn `x + y` ungerade ist. Bei einer Verschiebung
mit gerader Quersumme — etwa `(2, 2)`, wobei sich `x + y` überall um vier
ändert — sieht das Schachbrett danach exakt gleich aus wie vorher. Der Test
verglich zwei Bilder, die aus dem falschen Grund übereinstimmten: nicht weil
das Muster korrekt am Ziel haftete, sondern weil das Schachbrettmuster gegen
genau diese Verschiebung blind ist. Der Kommentar in
`tests/unit/test_draw.c` hält das fest:

[source,c]
----
/* Die Verschiebung muss die Musterphase tatsächlich verändern können, sonst
 * prüft der Test nichts. Bei PAT_GRAY50 ist das Bit (x+y) & 1, also ist das
 * Muster gegen jede Verschiebung mit gerader Quersumme invariant. Deshalb
 * (3,4) mit ungerader Summe - und zur Sicherheit ein zweiter Durchgang mit
 * PAT_HATCH, dessen Phase auch waagerecht wandert. */
----

Selbst ein Fehler, der das Muster fälschlich am Objekt statt am Ziel verankert
hätte, wäre mit der alten Verschiebung unentdeckt geblieben. Die Lehre: eine
Testeingabe kann zufällig genau die Eigenschaft verdecken, die sie beweisen
soll.

**Zwei Fenster, die sich nicht berühren.** M6 führte überlappende Fenster ein:
von hinten nach vorn gezeichnet, von vorn nach hinten getroffen. Der
ursprüngliche Test für die Fensterverwaltung benutzte zwei Fenster, die sich
gar nicht überlappten. Ob die Trefferprüfung — welches Fenster einen Klick an
einer bestimmten Stelle bekommt — in der richtigen Reihenfolge lief, blieb
deshalb unbemerkt: ohne Überlappung gibt es an keiner Stelle zwei Fenster, die
um denselben Klick konkurrieren könnten. Die Reparatur steht in
`tests/unit/test_wm.c`, als zwei eigene Tests mit sich überlappenden
Rechtecken:

[source,c]
----
rect    fa = rect_make(20, 20, 160, 120);
rect    fb = rect_make(100, 60, 160, 120);   /* überlappt a */
window *a  = wm_open(m, fa, "A", WIN_NORMAL);
window *b  = wm_open(m, fb, "B", WIN_NORMAL);
...
/* Ein Punkt, der in beiden Rahmen liegt. */
int x = 130, y = 100;
CHECK(rect_contains(fa, x, y));
CHECK(rect_contains(fb, x, y));

hit_part part = HIT_NONE;
CHECK(wm_hit(m, x, y, &part) == b);
----

Erst mit einem Punkt, der in beiden Fenstern liegt, prüft der Test überhaupt
etwas über die Reihenfolge. Der Commit dazu nennt die beiden Tests beim Namen:
`overlap_is_hit_front_to_back` und `overlap_is_drawn_back_to_front` — beide
Richtungen einzeln festgenagelt.

**Ein Tab zu wenig.** Der Dialog aus M7 lässt sich mit kbd:[Tab] zwischen
seinen Knöpfen bewegen, mit Umbruch am Ende zurück zum ersten. Bei zwei
Knöpfen ist das eine Falle für den Test selbst: prüft man den Fokus erst nach
*zwei* Tabs, landet man beim Knopf, bei dem man auch ohne jeden Umbruch
gelandet wäre — ein Test, der nach zwei Tabs prüft, kann also gar nicht
unterscheiden, ob der Umbruch tatsächlich passiert ist. Genau das stand im
ursprünglichen Test. `tests/unit/test_dialog.c` korrigiert es mit einem
Kommentar, der die Falle benennt:

[source,c]
----
/* Nach EINEM Tab prüfen, nicht erst nach zweien. Bei zwei Knöpfen landet
 * man sonst mit und ohne Umbruch am selben Ort - der Test könnte also nicht
 * unterscheiden. */
event tab = { .kind = EV_KEY_DOWN, .key = KEY_TAB };
CHECK(dialog_event(d, &tab));   /* Fokus 1 -> 0, also mit Umbruch */
----

Eine Mutation, die den Umbruch ganz entfernt, wäre mit der alten Prüfung nach
zwei Tabs unentdeckt geblieben — mit der neuen, nach genau einem, schlägt sie
zuverlässig fehl.

**Ein Test, der hängt statt fehlzuschlagen.** Bei den Mutationstests zur
Menüleiste (M7 Teil 3) ließ eine Mutation — die Schrittgrenze beim
Weiterrücken durch die Einträge entfernt — einen Test nicht fehlschlagen,
sondern in einer Endlosschleife hängen bleiben. Das ist schlimmer als ein
Fehlschlag: ein hängender Test blockiert den gesamten Lauf, statt sich zu
melden, und jeder Test danach kommt nie zu Wort — dasselbe Problem wie bei
einem abstürzenden Test, nur ohne dass irgendetwas auf dem Bildschirm
verrät, was passiert ist. Die Antwort steht seither in `CMakeLists.txt`, für
jeden einzelnen Test:

[source,cmake]
----
set_tests_properties(${name} PROPERTIES TIMEOUT 30)
----

Dreißig Sekunden sind für Tests, die normalerweise Sekundenbruchteile
brauchen, reichlich Luft — und genug, damit ein hängender Test als
`Timeout` gemeldet wird statt den ganzen Lauf lahmzulegen.

Keiner dieser vier Fälle wäre beim bloßen Lesen des Testcodes aufgefallen —
jeder Test sah für sich betrachtet vernünftig aus. Erst der Versuch, ihn
absichtlich scheitern zu lassen, zeigte, dass er es nicht konnte.

=== Der Sanitizer sieht, was die Suite übersieht

Ein Test kann nur das prüfen, worauf er achtet — und ein Speicherfehler
äußert sich oft gar nicht dort, wo er passiert. Genau das erlebte das Projekt
bei einem gemeldeten Absturz: ein Klick auf das Schließfeld links in der
Titelleiste ließ das ganze Programm abstürzen, obwohl die gesamte Testsuite
grün war. Die Ursache: die Fensterverwaltung schloss ein Fenster selbst,
sobald der Nutzer das Schließfeld traf, aber der Eigentümer des Fensters
erfuhr davon nichts. Die Vorführung hielt danach einen Zeiger auf bereits
freigegebenen Speicher und zeichnete beim nächsten Bild hinein — ein Fehler,
der erst beim nächsten Zeichenaufruf sichtbar wurde, nicht an der Stelle, wo
er entstand.

Damit so etwas nicht wieder unbemerkt bleibt, gibt es `make asan`:

[source,make]
----
asan:
	@cmake -S . -B $(BUILD)-asan -DPDA_SANITIZE=ON >/dev/null
	@cmake --build $(BUILD)-asan
	@ctest --test-dir $(BUILD)-asan --output-on-failure
----

Ein *Sanitizer* ist ein Werkzeug, das der Compiler in das Programm einbaut und
das zur Laufzeit mitprotokolliert, welcher Speicher gerade gültig ist. Greift
das Programm auf Speicher zu, der bereits freigegeben wurde, meldet der
Sanitizer genau das — mit der Stelle, an der freigegeben wurde, und der
Stelle, an der fälschlich noch zugegriffen wurde. `CMakeLists.txt` schaltet
dafür `-fsanitize=address,undefined` zu, in einem eigenen Bauverzeichnis, das
neben dem normalen bestehen bleibt. Mit der zurückgenommenen Reparatur meldet
`make asan` die Stelle samt beider Aufrufpfade; mit der Reparatur laufen alle
Suiten sauber durch.

Die Lehre daraus ist unbequem, aber wichtig: eine grüne Testsuite beweist
nicht, dass kein Speicherfehler vorliegt — sie beweist nur, dass keiner der
Tests einen ausgelöst hat, an einer Stelle, an der es auffiel. Ein
Speicherfehler fällt eben nur auf, wenn jemand hinsieht, und der Sanitizer ist
das Werkzeug, das genauer hinsieht als das bloße Ergebnis eines Tests.

=== Der Wächter, der zuerst selbst geprüft werden musste

Nicht jeder Test prüft Bilder oder Zustände. `tests/no_hardcoded_text.sh` ist
ein anderer Fall: ein Skript, das den Quelltext selbst durchsucht und dafür
sorgt, dass kein sichtbarer Text fest im Code steht, sondern über den
Textkatalog kommt (Kapitel 13 erklärt den Katalog selbst). Geprüft wird eng:
an `gfx_text` darf kein Zeichenkettenliteral als Text gehen, an `wm_open`
keines als Titel.

Beim Schreiben dieses Wächters stellten sich zwei Schwächen heraus, und beide
sind lehrreich, weil sie zeigen, dass ein Wächter genauso geprüft werden muss
wie das, was er bewacht.

Die erste: ein Aufruf wie `wm_open(m, rect, "Text", WIN_NORMAL)` steht im
Quelltext oft nicht in einer einzigen Zeile, sondern über mehrere verteilt,
mit Zeilenumbrüchen zwischen den Argumenten. Ein Wächter, der zeilenweise
sucht, würde einen solchen Aufruf einfach übersehen — nicht weil er falsch
prüft, sondern weil er nie hinschaut, wo der verbotene Text tatsächlich
steht. Die Lösung steht im Kommentar am Kopf der Datei:

[source,bash]
----
# Aufrufe stehen oft über mehrere Zeilen, deshalb wird jede Datei vor der Suche
# zu einer einzigen Zeile zusammengezogen. Damit entfällt die Zeilennummer;
# dafür entgeht uns kein umbrochener Aufruf.
----

Jede Datei wird vor der Suche mit `tr '\n' ' '` in eine einzige Zeile
verwandelt. Der Preis dafür: die Fehlermeldung kann keine Zeilennummer mehr
nennen, nur noch den Dateinamen. Ein bewusster Tausch — lieber jeden Fund
melden, ohne genau zu sagen wo, als manche Funde gar nicht zu melden.

Die zweite Schwäche traf ausgerechnet den richtigen Weg: der Aufruf
`T(cat, "schlüssel")`, mit dem sichtbarer Text korrekt über den Katalog
geholt wird, hat selbst ein Zeichenkettenliteral als Argument — seinen
Schlüssel. Ein Wächter, der stur nach Zeichenkettenliteralen sucht, hätte
also ausgerechnet den korrekten Aufruf als Fehler gemeldet. Die Lösung blendet
Katalogaufrufe vor der eigentlichen Suche aus:

[source,bash]
----
# Katalogaufrufe ausblenden: T(cat, "schlüssel") ist genau der richtige Weg,
# sein Literal darf den Wächter also nicht auslösen.
flat=$(tr '\n' ' ' < "$f" | sed -E 's/T[fn]?\([^()]*\)/KATALOG/g')
----

Beide Schwächen führen zur selben Lehre: einen Wächter reicht es nicht, an
einer einzigen Stelle zu prüfen, ob er falschen Code erkennt. Man muss auch
prüfen, ob er *richtigen* Code in Ruhe lässt — sonst verliert er, sobald er
den ersten korrekten Aufruf fälschlich meldet, das Vertrauen aller, die ihn
danach ignorieren. Ein Wächter, der nie anschlägt, ist nutzlos. Einer, der
ständig zu Unrecht anschlägt, ist es genauso.

=== Zum Ausprobieren

. Baue absichtlich einen Fehler in `apply_mode` in `src/gfx/draw.c` ein —
  vertausche etwa `GFX_OR` und `GFX_XOR` — und lass die Testsuite laufen.
  Welcher Test schlägt fehl? Wenn keiner fehlschlägt: welche Eingabe müsste
  ein Test wählen, damit er den Unterschied überhaupt sehen könnte?

. Lies dir `tests/unit/test_wm.c` an der Stelle `overlap_is_drawn_back_to_front`
  durch und vertausche in `wm_draw` versuchsweise die Zeichenreihenfolge.
  Prüfe mit `make test`, ob genau dieser Test es meldet.

. Ändere ein Sollbild unter `tests/golden/` von Hand — kippe ein einzelnes
  Zeichen bei einer P1-Datei — und lass `make test` laufen. Sieh dir an, was
  der Testläufer dazu ausgibt, und vergleiche es mit der `.actual`-Datei, die
  daraufhin entsteht.

. Baue in `tests/no_hardcoded_text.sh` versuchsweise die Ausblendung von
  Katalogaufrufen aus (entferne die Zeile mit `sed -E`) und lass es über den
  Quelltext laufen. Zähl nach, wie viele falsche Meldungen dabei entstehen.
