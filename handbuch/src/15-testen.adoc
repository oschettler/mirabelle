== Wie wir prüfen, ob es stimmt

Ein Test, der nie fehlschlägt, ist nicht automatisch ein guter Test — er
könnte auch einfach nichts prüfen. Dieses Kapitel handelt nicht davon, wie man
Tests schreibt, das siehst du an jeder Datei unter `tests/unit/`. Es handelt
davon, wie man herausfindet, ob ein Test überhaupt etwas taugt.

=== Ein Testläufer ohne Magie

`tests/test.h` ist knapp achtzig Zeilen lang, und das ist Absicht, kein
Zufall. Der Kopf der Datei sagt es geradeheraus:

[source,c]
----
/* Der Testläufer des Projekts. Bewusst klein und ohne Magie:
 * Ein Test ist eine Funktion, main() zählt sie auf. Mehr braucht es nicht.
 *
 *     TEST(bitmap_pset) { CHECK_EQ(1, 1); }
 *     int main(void) { RUN(bitmap_pset); return test_summary(); }
 */
----

`TEST(name)` ist nichts weiter als ein Makro, das zu `static void name(void)`
wird. Kein Testframework registriert die Funktion automatisch, keine
Reflexion sucht sie im Programm zusammen — jede Testdatei zählt ihre Tests in
`main` selbst auf, mit `RUN(name)`. Das wirkt altmodisch, verglichen mit
Frameworks, die Tests über Annotationen finden. Es hat aber einen Vorteil: es
gibt keine Stelle, an der Magie passiert, die du nicht lesen könntest. Wenn
ein Test nicht läuft, liegt es nicht daran, dass ihn irgendein Mechanismus
übersehen hat — er steht entweder in der `RUN`-Liste in `main`, oder nicht,
und das siehst du auf einen Blick.

`RUN` selbst macht drei Dinge: den Namen merken, zählen, aufrufen, und danach
melden, ob etwas fehlgeschlagen ist:

[source,c]
----
#define RUN(fn)                                                               \
    do {                                                                      \
        test_current = #fn;                                                   \
        test_failed_here = 0;                                                 \
        test_count++;                                                         \
        fn();                                                                 \
        if (test_failed_here) {                                               \
            test_failed++;                                                    \
            printf("FEHLER  %s\n", #fn);                                      \
        } else {                                                              \
            printf("ok      %s\n", #fn);                                      \
        }                                                                     \
    } while (0)
----

`CHECK(cond)` prüft eine Bedingung und merkt sich einen Fehlschlag, macht aber
weiter — die restlichen Prüfungen im selben Test laufen trotzdem, und du
siehst am Ende alle Fehler auf einmal statt nur den ersten.

Daneben gibt es `REQUIRE`, und der Unterschied ist wichtig genug, dass der
Kommentar in `tests/test.h` ihn eigens erklärt:

[source,c]
----
/* Wie CHECK, bricht den Test aber ab. Für Bedingungen, ohne die die folgenden
 * Zeilen abstürzen würden - typisch ein Zeiger, der nicht NULL sein darf. Ein
 * abstürzender Test ist schlimmer als ein fehlschlagender: er verschluckt alle
 * Ergebnisse, die nach ihm kämen. */
#define REQUIRE(cond)                                                         \
    do {                                                                      \
        if (!(cond)) {                                                        \
            TEST_FAIL("%s ist nicht wahr, Test abgebrochen", #cond);          \
            return;                                                           \
        }                                                                     \
    } while (0)
----

Der Unterschied ist der zwischen einer Prüfung, die scheitern darf, ohne dass
danach alles zusammenbricht, und einer Voraussetzung, ohne die gar nichts mehr
Sinn ergibt. `wm_create` liefert zum Beispiel entweder einen gültigen Zeiger
oder `NULL` — ruft ein Test danach ungeprüft `wm_open` auf einem
`NULL`-Zeiger auf, stürzt das ganze Testprogramm ab, und jeder Test danach in
der `RUN`-Liste wird nie ausgeführt. Deshalb steht an solchen Stellen
`REQUIRE(m)`, nicht `CHECK(m)`.

=== Sollbilder: ein Bild als Beweis

Der Kern des Projekts zeichnet in eine `bitmap` — Kapitel 5 erklärt, wie sie
aufgebaut ist. Ein Test, der prüfen will, ob eine Zeichnung stimmt, kann also
nicht bloß eine Zahl vergleichen. Er zeichnet, speichert das Ergebnis als PBM
und vergleicht es mit einer gespeicherten Vorlage — dem *Sollbild*. Das
übernimmt `tests/support/golden.c`, mit zwei Funktionen für zwei
verschiedene Bildgrößen:

[source,c]
----
golden_check()      für Ausschnitte, speichert P1 (Text, im Diff lesbar).
golden_check_full() für Vollbilder, speichert P4 (binär, kompakt).
----

Das PBM-Format kennt zwei Varianten, und `src/gfx/pbm.h` legt fest, wofür
welche gilt:

[source,c]
----
/* Lesen und Schreiben von PBM-Dateien (Portable Bitmap).
 *
 * Zwei Varianten, mit einer Größenregel dahinter:
 *
 *   P1 (Text)   ein Zeichen je Pixel. Ein Vollbild mit 800 x 480 wäre so rund
 *               750 kB groß. Deshalb nur für Ausschnitte - dafür zeigt
 *               "git diff" die Änderung lesbar an.
 *   P4 (binär) ein Bit je Pixel, also genau unser Speicherformat. Ein Vollbild
 *               mit 800 x 480 sind 48 000 Bytes. Für Vollbilder, und davon nur
 *               eine Handvoll.
 */
----

Rechne die zweite Zahl selbst nach: 800 × 480 Pixel bei einem Bit je Pixel
sind `800 / 8 = 100` Bytes je Zeile (Kapitel 5 leitet diese Rechnung her), mal
480 Zeilen, macht genau 48 000 Bytes — egal wie das Bild aussieht, weil P4 den
Bildspeicher unverändert herausschreibt. Ein Textsollbild desselben Bilds wäre,
wie der Kommentar sagt, rund 750 kB groß: statt eines Bits braucht ein Pixel
im Textformat ein ganzes Zeichen, dazu kommen Zeilenumbrüche. Ein paar solche
Dateien im Repository, und `git diff` würde bei jeder kleinsten Änderung
Hunderttausende Zeichen anzeigen, die niemand liest.

Deshalb ist P1 nur für Ausschnitte gedacht, kleine Bereiche wie einen
Fensterrahmen oder eine Textzeile, bei denen die Textform ihren eigentlichen
Zweck erfüllt: `git diff` zeigt eine Änderung als lesbares Bitmuster an, nicht
als unleserlichen Bytehaufen. Und diese Regel steht nicht nur im Kommentar —
`golden_check` erzwingt sie:

[source,c]
----
bool golden_check(const char *name, const bitmap *bm)
{
    if ((long)bm->w * bm->h > GOLDEN_MAX_P1_PIXELS) {
        printf("  %s ist mit %dx%d zu groß für ein Textsollbild.\n",
               name, bm->w, bm->h);
        printf("  Nimm einen Ausschnitt oder golden_check_full() für P4.\n");
        return false;
    }
    return check(name, bm, false);
}
----

`GOLDEN_MAX_P1_PIXELS` ist `256 * 256`. Ein Test, der versehentlich ein
Vollbild an `golden_check` statt `golden_check_full` übergibt, scheitert also
nicht leise mit einer riesigen Textdatei im Repository, sondern laut, mit
einer Meldung, die sagt, was zu tun ist. `tests/unit/test_golden.c` prüft
sogar genau das als eigenen Test, mit dem Kommentar: „Die Größenregel steht im
Code, nicht nur in der Dokumentation.“ Eine Regel, die nur in der Doku steht,
wird irgendwann vergessen. Eine, die der Code selbst durchsetzt, nicht.

=== Erst hinsehen, dann übernehmen

Was aber, wenn sich ein Bild absichtlich ändert — weil du dem Programm
tatsächlich beigebracht hast, etwas anders zu zeichnen? Dann braucht es ein
neues Sollbild. `make test ACCEPT=1` schreibt es:

[source,make]
----
test: all
	@PDA_GOLDEN_ACCEPT=$(ACCEPT) ctest --test-dir $(BUILD) --output-on-failure
----

`golden_check` liest die Umgebungsvariable `PDA_GOLDEN_ACCEPT` und schreibt,
wenn sie gesetzt ist, statt zu vergleichen. Das ist bequem — und genau deshalb
gefährlich. Ein Sollbild ist nur so gut wie die Prüfung, die vor seiner
Übernahme stattfand. Wer `ACCEPT=1` setzt, ohne das neu geschriebene Bild
anzusehen, überschreibt möglicherweise gerade den Beweis dafür, dass etwas
kaputt ist, mit dem kaputten Zustand selbst. Von da an ist die kaputte Version
das neue Soll, und der Test wird nie wieder etwas melden — nicht weil alles
stimmt, sondern weil niemand mehr hinschaut.

Die Regel ist deshalb: erst hinsehen, dann übernehmen. Bei einem
Textausschnitt heißt das, das PBM tatsächlich zu lesen oder die Meldung beim
Fehlschlag zu prüfen — `golden.c` druckt bei einer Abweichung den betroffenen
Bereich als ASCII-Bild in die Konsole. Bei einem Vollbild bedeutet es, die
`.actual`-Datei anzusehen, die bei jedem Fehlschlag neben dem Sollbild
entsteht. Wer `ACCEPT=1` blind läuft, um eine rote Testsuite grün zu bekommen,
hat am Ende keine Sollbilder mehr — nur noch Dateien, die zufällig zu dem
passen, was der Code gerade tut.

=== Mutationstests: prüft der Test wirklich das, was er soll?

Das ist die schwierigere und wichtigere Frage. Ein grüner Test beweist nicht,
dass der Code richtig ist — er beweist nur, dass die gewählten Eingaben nicht
durch den vorhandenen Fehler gefallen sind. Ob der Test einen Fehler
überhaupt *entdecken könnte*, ist eine eigene Frage, und die einzige Methode,
sie zu beantworten, ist: absichtlich einen Fehler einbauen und schauen, ob
wenigstens ein Test anschlägt. Das nennt man einen Mutationstest. Bleibt die
Suite grün, obwohl der Code jetzt falsch ist, hat sie diese Stelle nie
wirklich geprüft, egal wie viele grüne Zeilen sie ausgibt.

Etwa ein Drittel aller Lücken in diesem Projekt kam so ans Licht. Vier davon
stehen hier, weil sie vier verschiedene Arten zeigen, wie ein Test versagen
kann, ohne dass man es ihm ansieht. Jede davon ist eine Regel für den nächsten
Test.

**Eine Eingabe darf nicht gegen den Fehler blind sein.** Kapitel 5 erklärt,
dass ein gezeichnetes Muster am Zielbild haftet, nicht am gezeichneten Objekt —
ein graues Rechteck sieht überall auf dem Bildschirm gleich aus. Prüfen lässt
sich das, indem man dasselbe Rechteck über zwei verschiedene `origin`-Werte
verschiebt und die Ergebnisse vergleicht. Nur: `PAT_GRAY50`, das
Schachbrettmuster, setzt ein Bit genau dann, wenn `x + y` ungerade ist. Bei
einer Verschiebung mit gerader Quersumme — etwa `(2, 2)`, wobei sich `x + y`
überall um vier ändert — sieht das Schachbrett danach exakt gleich aus wie
vorher. Ein solcher Vergleich stimmt aus dem falschen Grund überein: nicht
weil das Muster korrekt am Ziel haftet, sondern weil das Muster gegen genau
diese Verschiebung blind ist. Der Kommentar in `tests/unit/test_draw.c` hält
die Regel fest:

[source,c]
----
/* Die Verschiebung muss die Musterphase tatsächlich verändern können, sonst
 * prüft der Test nichts. Bei PAT_GRAY50 ist das Bit (x+y) & 1, also ist das
 * Muster gegen jede Verschiebung mit gerader Quersumme invariant. Deshalb
 * (3,4) mit ungerader Summe - und zur Sicherheit ein zweiter Durchgang mit
 * PAT_HATCH, dessen Phase auch waagerecht wandert. */
----

Ein Fehler, der das Muster fälschlich am Objekt statt am Ziel verankert, bliebe
mit einer geraden Verschiebung unentdeckt. Eine Testeingabe kann genau die
Eigenschaft verdecken, die sie beweisen soll — und ob sie das tut, sieht man
ihr nicht an, man muss es ausrechnen.

**Was einander nie begegnet, prüft keine Reihenfolge.** Fenster werden von
hinten nach vorn gezeichnet und von vorn nach hinten getroffen. Zwei Fenster,
die sich nicht überlappen, prüfen davon nichts: es gibt keine Stelle, an der
zwei von ihnen um denselben Klick konkurrieren. `tests/unit/test_wm.c` legt sie
deshalb absichtlich übereinander:

[source,c]
----
rect    fa = rect_make(20, 20, 160, 120);
rect    fb = rect_make(100, 60, 160, 120);   /* überlappt a */
window *a  = wm_open(m, fa, "A", WIN_NORMAL);
window *b  = wm_open(m, fb, "B", WIN_NORMAL);
...
/* Ein Punkt, der in beiden Rahmen liegt. */
int x = 130, y = 100;
CHECK(rect_contains(fa, x, y));
CHECK(rect_contains(fb, x, y));

hit_part part = HIT_NONE;
CHECK(wm_hit(m, x, y, &part) == b);
----

Erst ein Punkt, der in beiden Fenstern liegt, prüft überhaupt etwas über die
Reihenfolge. `overlap_is_hit_front_to_back` und `overlap_is_drawn_back_to_front`
nageln beide Richtungen einzeln fest.

**Prüfe nach einem Schritt, nicht nach zweien.** Ein Dialog lässt sich mit
kbd:[Tab] zwischen seinen Knöpfen bewegen, mit Umbruch am Ende zurück zum
ersten. Bei zwei Knöpfen ist das eine Falle: nach *zwei* Tabs steht der Fokus
dort, wo er auch ohne jeden Umbruch stünde. `tests/unit/test_dialog.c` benennt
sie im Kommentar:

[source,c]
----
/* Nach EINEM Tab prüfen, nicht erst nach zweien. Bei zwei Knöpfen landet
 * man sonst mit und ohne Umbruch am selben Ort - der Test könnte also nicht
 * unterscheiden. */
event tab = { .kind = EV_KEY_DOWN, .key = KEY_TAB };
CHECK(dialog_event(d, &tab));   /* Fokus 1 -> 0, also mit Umbruch */
----

Eine Mutation, die den Umbruch ganz entfernt, bliebe nach zwei Tabs
unentdeckt; nach genau einem schlägt sie zuverlässig fehl.

**Ein hängender Test ist schlimmer als ein fehlschlagender.** Nicht jede
Mutation lässt einen Test fehlschlagen — manche lassen ihn in einer
Endlosschleife stehen, etwa wenn die Schrittgrenze beim Weiterrücken durch
Menüeinträge entfällt. Ein hängender Test blockiert den ganzen Lauf: jeder
Test danach kommt nie zu Wort, und nichts verrät, was passiert ist. Die
Antwort steht in `CMakeLists.txt`, für jeden einzelnen Test:

[source,cmake]
----
set_tests_properties(${name} PROPERTIES TIMEOUT 30)
----

Dreißig Sekunden sind für Tests, die normalerweise Sekundenbruchteile
brauchen, reichlich Luft — und genug, damit ein hängender Test als
`Timeout` gemeldet wird statt den ganzen Lauf lahmzulegen.

Keine dieser vier Fallen sieht man einem Test beim Lesen an — jeder von ihnen
sieht für sich betrachtet vernünftig aus. Erst der Versuch, ihn absichtlich
scheitern zu lassen, zeigt, ob er es kann.

=== Der Sanitizer sieht, was die Suite übersieht

Ein Test kann nur das prüfen, worauf er achtet — und ein Speicherfehler äußert
sich oft gar nicht dort, wo er passiert.

Der typische Fall sieht so aus: die Fensterverwaltung schließt ein Fenster
selbst, sobald der Nutzer das Schließfeld trifft. Wer einen Zeiger darauf hält
und das nicht mitbekommt, zeichnet beim nächsten Bild in freigegebenen
Speicher. Das Programm stürzt ab — beim *nächsten* Zeichenaufruf, nicht an der
Stelle, an der der Fehler entstand. Die Testsuite bleibt dabei grün, weil kein
Test das Fenster nach dem Schließen anfasst.

Dagegen gibt es `make asan`:

[source,make]
----
asan:
	@cmake -S . -B $(BUILD)-asan -DPDA_SANITIZE=ON >/dev/null
	@cmake --build $(BUILD)-asan
	@ctest --test-dir $(BUILD)-asan --output-on-failure
----

Ein *Sanitizer* ist ein Werkzeug, das der Compiler ins Programm einbaut und
das zur Laufzeit mitprotokolliert, welcher Speicher gerade gültig ist. Greift
das Programm auf bereits freigegebenen Speicher zu, meldet der Sanitizer
genau das, mit beiden Stellen: wo freigegeben wurde, und wo fälschlich noch
zugegriffen wurde. `CMakeLists.txt` schaltet dafür `-fsanitize=address,undefined`
zu, in einem eigenen Bauverzeichnis neben dem normalen.

Probier es aus: nimm die Rückmeldung `window_set_on_close` aus Kapitel 7
versuchsweise heraus. `make test` bleibt grün, `make asan` nennt die Stelle
samt beider Aufrufpfade.

Die Regel dahinter ist unbequem, aber wichtig: eine grüne Testsuite beweist
nicht, dass kein Speicherfehler vorliegt — nur, dass keiner der Tests einen an
einer Stelle ausgelöst hat, an der er auffiel.

=== Ein Wächter muss selbst geprüft werden

Nicht jeder Test prüft Bilder oder Zustände. `tests/no_hardcoded_text.sh` ist
ein anderer Fall: ein Skript, das den Quelltext selbst durchsucht und dafür
sorgt, dass kein sichtbarer Text fest im Code steht, sondern über den
Textkatalog kommt. Geprüft wird eng: an `gfx_text` darf kein
Zeichenkettenliteral als Text gehen, an `wm_open` keines als Titel.

Ein Wächter hat zwei Arten zu versagen, und beide sind leise: er übersieht
etwas, oder er meldet etwas Falsches. Beides muss man ihm ansehen können,
bevor man sich auf ihn verlässt.

Das erste: ein Aufruf wie `wm_open(m, rect, "Text", WIN_NORMAL)` steht im
Quelltext oft nicht in einer einzigen Zeile, sondern über mehrere verteilt.
Ein Wächter, der zeilenweise sucht, übersieht ihn — nicht weil er falsch
prüft, sondern weil er nie hinschaut, wo der verbotene Text steht. Die Antwort
steht im Kommentar am Kopf der Datei:

[source,bash]
----
# Aufrufe stehen oft über mehrere Zeilen, deshalb wird jede Datei vor der Suche
# zu einer einzigen Zeile zusammengezogen. Damit entfällt die Zeilennummer;
# dafür entgeht uns kein umbrochener Aufruf.
----

Jede Datei wird vor der Suche mit `tr '\n' ' '` in eine einzige Zeile
verwandelt. Der Preis dafür: die Fehlermeldung kann keine Zeilennummer mehr
nennen, nur noch den Dateinamen. Ein bewusster Tausch — lieber jeden Fund
melden, ohne genau zu sagen wo, als manche Funde gar nicht zu melden.

Das zweite trifft ausgerechnet den richtigen Weg: der Aufruf
`T(cat, "schlüssel")`, mit dem sichtbarer Text korrekt über den Katalog geholt
wird, hat selbst ein Zeichenkettenliteral als Argument — seinen Schlüssel. Ein
Wächter, der stur nach Literalen sucht, meldet also ausgerechnet den korrekten
Aufruf. Deshalb werden Katalogaufrufe vor der eigentlichen Suche ausgeblendet:

[source,bash]
----
# Katalogaufrufe ausblenden: T(cat, "schlüssel") ist genau der richtige Weg,
# sein Literal darf den Wächter also nicht auslösen.
flat=$(tr '\n' ' ' < "$f" | sed -E 's/T[fn]?\([^()]*\)/KATALOG/g')
----

Beides führt zur selben Regel: es reicht nicht zu prüfen, ob ein Wächter
falschen Code erkennt. Er muss auch *richtigen* Code in Ruhe lassen. Ein
Wächter, der einen korrekten Aufruf meldet, verliert das Vertrauen aller — und
wird danach ignoriert, auch wenn er einmal recht hat.

Denselben Dienst tut `tests/plat_count.sh`: es zählt die Deklarationen in
`src/plat/plat.h` und vergleicht sie mit der Zahl, die Header, `DESIGN.md` und
dieses Buch nennen. Wo eine Angabe im Text von etwas Zählbarem abhängt, ist ein
Test billiger als Aufmerksamkeit.

=== Zum Ausprobieren

. Baue absichtlich einen Fehler in `apply_mode` in `src/gfx/draw.c` ein —
  vertausche etwa `GFX_OR` und `GFX_XOR` — und lass die Testsuite laufen.
  Welcher Test schlägt fehl? Falls keiner: welche Eingabe müsste ein Test
  wählen, damit er den Unterschied überhaupt sehen könnte?

. Vertausche in `wm_draw` versuchsweise die Zeichenreihenfolge und prüfe mit
  `make test`, ob `overlap_is_drawn_back_to_front` aus `tests/unit/test_wm.c`
  es meldet.

. Ändere ein Sollbild unter `tests/golden/` von Hand — kippe ein einzelnes
  Zeichen bei einer P1-Datei — und lass `make test` laufen. Vergleiche die
  Ausgabe mit der `.actual`-Datei, die daraufhin entsteht.

. Entferne in `tests/no_hardcoded_text.sh` die Zeile mit `sed -E`, die
  Katalogaufrufe ausblendet, und lass es über den Quelltext laufen. Zähl
  nach, wie viele falsche Meldungen dabei entstehen.

. Ändere im Kopf von `src/plat/plat.h` die Zahl der Funktionen auf eine
  falsche und lass `make test` laufen. Welcher Test meldet sich, und was
  genau vergleicht er?
