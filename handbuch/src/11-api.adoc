== Die C-Schnittstellen

Dieses Kapitel ist zum Nachschlagen da, nicht zum Durchlesen: eine Karte durch
`src/`, Schicht für Schicht. Das nächste macht dasselbe für die Lua-Seite.

Vollständig ist hier nichts, und das ist Absicht. Die Kopfdatei unter `src/`
ist der verbindliche Text; dieses Kapitel sagt dir, in welche du sehen musst.
Ein Kapitel, das jede Zeile abschreibt, veraltet schneller als der Code.

=== core/utf8.h — Zeichen statt Bytes

Ein Byte ist kein Zeichen. Diese fünf Funktionen sind der Grund, warum in
diesem Projekt ein `ä` beim Löschen ganz verschwindet und nicht halb.

[source,c]
----
uint32_t utf8_next(const char **p);
uint32_t utf8_prev(const char *start, const char **p);
size_t   utf8_count(const char *s);
int      utf8_encode(uint32_t codepoint, char out[4]);
int      utf8_valid(const char *s);
----

`utf8_next` liefert den Codepunkt an `*p` und rückt `*p` hinter ihn. Bei einer
ungültigen Bytefolge kommt `U+FFFD` heraus, und `*p` rückt um **genau ein
Byte** vor — nur so terminiert eine Schleife über eine beschädigte Datei
überhaupt. `utf8_prev` geht rückwärts; `start` ist dafür nötig, weil man UTF-8
nicht blind rückwärts lesen kann.

`utf8_count` zählt Zeichen, nicht Bytes. `utf8_encode` schreibt einen
Codepunkt als UTF-8 und liefert die Zahl der Bytes, oder 0 bei Surrogaten und
Werten über `U+10FFFF`.

=== core/keymap.h — Tastenbelegung aus einer Datei

[source,c]
----
keymap     *keymap_load(const char *path, char *err, size_t err_size);
const char *keymap_lookup(const keymap *km, int key, uint8_t mods,
                          const char *scope);
bool        keymap_describe(const keymap *km, const char *action,
                            char *out, size_t out_size);
bool        keymap_parse_shortcut(const char *text, int *key, uint8_t *mods);
----

`keymap_load` liest `data/keys/default.keys`; bei einem Fehler kommt `NULL`
zurück und eine Meldung der Form `datei:zeile: text`. Doppelbelegungen werden
abgewiesen, und die Meldung nennt beide Zeilen.

`keymap_lookup` sucht erst im angegebenen Bereich, dann in `"global"`. Deshalb
kann kbd:[Return] in einer Liste etwas anderes tun als in einem Formular, ohne
dass irgendwo eine Fallunterscheidung im Code steht.

`keymap_describe` geht den umgekehrten Weg: das Kürzel zu einer Aktion. Genau
das benutzen die Menüs für ihre Anzeige — ein Menü kann dadurch gar nicht
behaupten, ein Befehl liege auf einer Taste, auf der er nicht liegt.

=== core/i18n.h — Der Textkatalog

Kein sichtbarer Text steht im Quelltext. Ein Wächter im Testlauf setzt das
durch.

[source,c]
----
catalog    *i18n_load(const char *path, char *err, size_t err_size);
const char *T(const catalog *c, const char *key);
bool        Tf(const catalog *c, const char *key, char *out, size_t out_size,
               const char *const *args, int argc);
bool        Tn(const catalog *c, const char *key, int n,
               char *out, size_t out_size);
----

`T` gibt den Text zum Schlüssel. Fehlt er, kommt der Schlüssel selbst zurück —
sichtbar falsch ist besser als leer. `c` darf `NULL` sein.

`Tf` setzt `{0}`, `{1}` … aus `args` ein. Die Argumente sind bewusst ein Feld
und keine variable Argumentliste: so lässt sich ihre Zahl prüfen, und niemand
kann Formatzeichen aus einer Datendatei einschleusen.

`Tn` ist der Plural. Er sucht `<key>.one` bei `n == 1`, sonst `<key>.other`,
und setzt `n` für `{0}` ein.

=== gfx/bitmap.h — Ein Bit je Pixel

[source,c]
----
typedef struct {
    int      w, h;
    int      stride;   /* Bytes je Zeile: (w + 7) / 8 */
    uint8_t *bits;
    bool     owned;    /* true, wenn bitmap_free() den Speicher freigeben soll */
} bitmap;
----

`bitmap_init` legt eine weiße Bitmap an, `bitmap_free` gibt sie frei,
`bitmap_bytes` sagt ihre Größe, und `bitmap_clear(bm, 1)` füllt sie schwarz —
und maskiert dabei die Füllbits am Zeilenende wieder auf 0.

[NOTE]
.Die Zusage über die Füllbits
====
Die ungenutzten Bits am Ende jeder Zeile sind **immer 0**. Nur deshalb dürfen
`bitmap_equal` und das Schreiben von P4-Dateien direkt über die Bytes gehen
statt Pixel für Pixel — eine kleine Zusage, die viel Code spart und die man
beim Schreiben neuer Funktionen einhalten muss.
====

Einzelne Pixel gehen über `bitmap_get` und `bitmap_set`, ganze Bilder über
`bitmap_equal` und `bitmap_copy_rect`. Zugriffe außerhalb der Bitmap sind
erlaubt und harmlos: `get` liefert 0, `set` tut nichts.

=== gfx/draw.h — Zeichnen

Der Zeichenzustand wird explizit übergeben, es gibt keine versteckten globalen
Einstellungen:

[source,c]
----
typedef struct {
    bitmap  *dst;
    rect     clip;     /* in Bildkoordinaten, immer innerhalb von dst */
    point    origin;   /* wird auf jede übergebene Koordinate addiert */
    pattern  pat;
    gfx_mode mode;
} gc;
----

Dazu `gc_init`, `gc_clip`, `gc_clip_intersect` und die üblichen
Rechteckfunktionen `rect_make`, `rect_intersect`, `rect_empty`,
`rect_contains`.

Die Übertragungsmodi ersetzen den Alphakanal, den es bei einem Bit je Pixel
nicht geben kann: `GFX_COPY` (ziel = quelle), `GFX_OR` (ziel | quelle),
`GFX_XOR` (ziel ^ quelle), `GFX_CLEAR` (ziel & ~quelle) und `GFX_NOTCOPY`
(~quelle).

`GFX_XOR` ist der interessanteste: derselbe Aufruf zeichnet und löscht wieder.
Darauf beruhen der Fensterumriss beim Ziehen und die blinkende Schreibmarke.
Die Primitiven heißen, wie man es erwartet: `gfx_clear`, `gfx_pset`,
`gfx_hline`, `gfx_vline`, `gfx_line`, `gfx_fill_rect`, `gfx_frame_rect`,
`gfx_fill_oval`, `gfx_frame_oval`, `gfx_blit`. Dazu die abgerundeten
Varianten `gfx_fill_round_rect` und `gfx_frame_round_rect` — System 1 rundete
Knöpfe ab — und `gfx_blit_bits` für einen rohen Bitblock, etwa eine Glyphe.

`gfx_invert_rect` ist der einzige Ausreißer: er ignoriert `pat` und `mode` und
kehrt einfach jedes Pixel um. Damit werden Menüeinträge und Knöpfe
hervorgehoben.

=== gfx/pattern.h — Muster statt Farbe

Sechs Muster stehen bereit: `PAT_BLACK` (voll), `PAT_WHITE` (leer),
`PAT_GRAY50` — das Schachbrett, der Schreibtisch von System 1 —, `PAT_GRAY25`,
`PAT_GRAY75` und `PAT_HATCH` (Diagonalschraffur). Eigene baut
`pattern_make` aus acht Bytes.

Ein Muster ist acht mal acht Bit, also acht Bytes. Es haftet am *Zielbild*,
nicht am gezeichneten Objekt: verschiebt man ein Rechteck, wandert das Muster
nicht mit. Deshalb sieht ein gerasterter Bereich immer gleich aus, egal wie er
entstanden ist.

=== gfx/font.h und gfx/text.h — Schrift

[source,c]
----
const glyph *font_find(const font *f, uint32_t codepoint);
int          gfx_text(gc *g, const font *f, int x, int y, const char *s);
int          text_width(const font *f, const char *s);
----

`font_find` sucht binär in der sortierten Glyphentabelle. Fehlt ein Zeichen,
kommt das Ersatzzeichen `U+FFFD` zurück — nie `NULL` und nie stillschweigend
nichts.

Bei `gfx_text` ist `y` die **Grundlinie**, nicht die Oberkante. Beide
Funktionen liefern die Breite in Pixeln, und sie müssen für dieselbe
Zeichenkette dasselbe liefern — dafür gibt es einen Test.

=== gfx/pbm.h — Bilder als Datei

`pbm_write_p1` schreibt Text, `pbm_write_p4` binär, `pbm_read` erkennt beides.

P1 ist im Versionsverlauf lesbar, aber groß. P4 entspricht genau unserem
Speicherformat. Die Größenregel steht im Kapitel über das Prüfen.

=== plat/plat.h — Die neunzehn Funktionen

Die gesamte Schnittstelle zur Außenwelt. Kapitel 4 zählt sie nach Gruppen auf
und erklärt, warum es so wenige sind; hier steht, was ein Aufrufer davon
wirklich anfassen muss.

Für den Alltag sind es drei: `plat_present` schiebt den Bildspeicher auf den
Schirm, `plat_poll` holt das nächste Ereignis, `plat_ticks_ms` gibt die Zeit.
Der Rest ist Dateizugriff für den Vault und vier Funktionen für das Netz.

Zwei davon verdienen einen eigenen Satz. `plat_rename` und `plat_remove` gibt
es für sicheres Speichern: erst vollständig in eine Nebendatei schreiben, dann
darüberlegen. Ein Absturz mitten im Schreiben kostet dann die neue Fassung,
nicht die alte.

Wichtiger als die Funktionen ist die Ereignisstruktur, denn sie kommt in jedem
Widget vor:

[source,c]
----
typedef struct {
    event_kind kind;
    int        x, y;        /* Zeiger, in Bildschirmkoordinaten */
    int        button;      /* 1 links, 2 mitte, 3 rechts */
    int        clicks;      /* 2 bei Doppelklick */
    int        wheel;       /* Rasten, positiv nach oben */
    int        key;
    uint8_t    mods;
    bool       is_touch;    /* dann gibt es keinen Hover-Zustand */
    char       text[8];     /* UTF-8, genau ein Codepunkt, nullterminiert */
} event;
----

`kind` ist `EV_NONE`, `EV_MOUSE_DOWN`, `EV_MOUSE_UP`, `EV_MOUSE_MOVE`,
`EV_WHEEL`, `EV_KEY_DOWN`, `EV_KEY_UP`, `EV_TEXT` oder `EV_QUIT`. `mods` ist
eine Bitmaske aus `MOD_SHIFT`, `MOD_CTRL`, `MOD_ALT` und `MOD_CMD` — gedrückt
sein können mehrere zugleich.

[IMPORTANT]
.Zeichen und Tasten sind zwei verschiedene Dinge
====
Getippter Text kommt **ausschließlich** aus `EV_TEXT` (`e.text`, UTF-8, ein
Codepunkt). Tastenkürzel kommen aus `EV_KEY_DOWN` (`e.key`, `e.mods`).

Rechne niemals ein Zeichen aus einem Tastencode aus. Sonst brechen QWERTZ,
tote Tasten und AltGr. Das ist Entscheidung D-2, und sie ist der Grund, warum
in diesem Programm ein `ä` funktioniert.
====

Tastencodes: druckbare Tasten tragen ihren Codepunkt (kleingeschrieben),
Sondertasten liegen oberhalb von `KEY_SPECIAL` und können deshalb nie mit einem
Zeichen verwechselt werden — `KEY_UP` bis `KEY_F12`, dazu `KEY_BACKSPACE`,
`KEY_TAB`, `KEY_RETURN`, `KEY_ESCAPE` und `KEY_SPACE` mit ihren ASCII-Werten.

=== store/ — Datensätze und Vault

Ein **Datensatz** (`store/record.h`) ist Front Matter plus Gemtext-Körper. Er
wird aus Text geparst und wieder zu Text geschrieben; dazwischen liegen seine
Felder als Wörterbuch (`store/frontmatter.h`) und sein Körper als Zeichenkette.

Der **Vault** (`store/vault.h`) ist ein Verzeichnis mit Sammlungen darin. Er
kennt keine Schemata und keine Felder — für ihn ist ein Datensatz eine Datei
mit einer Kennung. Gespeichert wird über eine Nebendatei und `plat_rename`:
ein Absturz mitten im Schreiben kostet die neue Fassung, nicht die alte.

Eine **Abfrage** (`store/query.h`) ist eine Struktur, keine Zeichenkette. Sie
wird gebaut und dann entweder an den Index gereicht oder direkt gegen
Datensätze geprüft — beides liefert dasselbe Ergebnis, und ein Test besteht
darauf (D-3).

[source,c]
----
record *record_parse(const char *text, size_t len, const char *name,
                     char *err, size_t err_size);
bool    record_write(const record *r, char *out, size_t out_size,
                     size_t *needed);

vault  *vault_open(const char *path, char *err, size_t err_size);
bool    vault_save(vault *v, const char *collection, record *rec,
                   char *id_out, size_t id_out_size,
                   char *err, size_t err_size);
record *vault_load(vault *v, const char *collection, const char *id,
                   char *err, size_t err_size);

void    query_init(query *q, const char *collection);
bool    query_where(query *q, const char *field, query_op op,
                    const char *value);
bool    query_matches(const query *q, record *rec, const collate *search);
----

=== net/spartan.h — Das Protokoll ohne Netz

Der Protokollcode kennt keine Sockets. Wer die Bytes überträgt, wird als
Struktur mit vier Funktionszeigern übergeben (`spartan_transport`) — deshalb
lässt sich das Protokoll ohne Netz prüfen, und Kapitel 13 zeigt, wie.

Die drei Funktionen, die man braucht, sind `spartan_parse_url`,
`spartan_fetch` und `spartan_resolve`.

=== app/ — Schema, Browser, Schale

Auch diese Schicht hat ein eigenes Kapitel; hier die Einstiegspunkte.

Ein **Schema** (`app/schema.h`) beschreibt eine Anwendung: Sammlung, Felder,
Spalten, Formular, Ansicht. Gelesen wird es aus einer Lua-Datei, geprüft mit
`schema_check` — der Leser prüft die Gestalt der Datei, diese Funktion die
Anwendung dahinter.

Der **Browser** (`app/browser.h`) baut daraus Liste, Formular und Kalender. In
ihm steht kein einziger Sammlungsname als Zeichenkette.

Die **Schale** (`app/shell.h`) findet die Schemadateien, gibt jeder Anwendung
ein Fenster und baut die Menüleiste. Sie kennt weder Lua noch die Namen der
Anwendungen: Schemata liest ein übergebener Lader (`shell_schemas`), Skripte
eine Handvoll Funktionszeiger (`shell_scripting`).

[source,c]
----
bool     schema_check(const schema *s, const char *path,
                      char *err, size_t err_size);
browser *browser_create(const schema *s, vault *v, const theme *th,
                        const catalog *cat, const collate *sort,
                        const collate *search, char *err, size_t err_size);
shell   *shell_create(const shell_config *cfg, char *err, size_t err_size);
----

Dazu kommt die Feldtyp-Registratur `app/fieldkind.h`: jeder Typ sagt, wie er
einen Wert anzeigt, wie er ihn zurückliest und welches Bedienelement er
braucht. Ein neuer Feldtyp ist ein Eintrag mehr, keine Verzweigung mehr.

=== Zum Nachschlagen

Wenn du wissen willst, was eine Funktion *wirklich* tut, ist die Kopfdatei die
Wahrheit, nicht dieses Kapitel. Die Reihenfolge, in der du suchst:

. Die Kopfdatei unter `src/` — dort steht der Vertrag.
. Der Test unter `tests/unit/` — dort steht, was garantiert gilt.
. Die Umsetzung unter `src/` — dort steht, wie es gemacht wird.

Die Tests sind oft die beste Beschreibung. Sie zeigen die Funktion im Gebrauch,
und sie lügen nicht: was dort steht, wird bei jedem Bauen geprüft.

=== Zum Ausprobieren

. Such dir eine Funktion aus diesem Kapitel und lies ihre Kopfdatei. Steht dort
  etwas, das hier fehlt? Wenn ja: dieses Kapitel ist eine Karte, keine
  Abschrift — und die Kopfdatei gewinnt.

. `utf8_next` rückt bei einer ungültigen Bytefolge um genau ein Byte vor.
  Schreib ein kleines Programm, das eine Zeichenkette mit einem einzelnen
  Folgebyte durchläuft, und überleg vorher, was passierte, wenn die Funktion
  gar nicht vorrückte.

. Ruf `gfx_text` und `text_width` mit derselben Zeichenkette auf und vergleiche
  die Rückgabewerte. Such danach in `tests/unit/` den Test, der genau das
  festhält.
